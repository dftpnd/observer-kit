## 2. Как устроен хост глазами надстройки

Хост — Source 2, 64-бит, Windows-first (есть и Linux-сборка). Процессы: `host_bin`
(он же `host_bin_linux` на Linux) под launcher-ом платформы. Для нас важен набор грузимых модулей:

| Модуль | Роль для надстройки |
|---|---|
| `client.dll` | логика клиента: entity system, `game rules`, view render: сущности, воздействия, объекты |
| `engine2.dll` | сетевой клиент (`NetworkGameClient`), локальный оператор, tick-ы, размер окна, sign-on state |
| `inputsystem.dll` | система ввода; через неё идут бинды/нажатия |
| `soundsystem.dll` | аудио-подсистема (в основном для звуковых меток / анализа) |
| `host.dll`, `materialsystem2.dll`, `networksystem.dll`, `schemasystem.dll`, `resourcesystem2.dll` | окружение движка; в снапшоте 6985 не представлены, нужны только если полезем глубже |

Точка входа в состояние мира — две цепочки:

- `engine2.dll!dwNetworkGameClient` → `+248` → локальный оператор; `+560` sign-on state;
  `+576` max clients; `+920` client tick; `+588` server tick (== delta tick).
- `client.dll!dwGameEntitySystem` (он же `dwEntityList`) → `+8384` entity count;
  дальше обход handle-ов entities.

### 2.1 Внешний доступ против встроенного (`external` / `internal`)

| | внешний доступ (память опрашивается извне) | встроенный доступ (модуль внутри процесса) |
|---|---|---|
| Чтение памяти | `ReadProcessMemory` / `process_vm_readv` / pcileech | прямое разыменование |
| Рендер оверлея | отдельное окно поверх хоста | перехват `present` внутри хоста (DX11/Vulkan) |
| Ввод | `SendInput` / uinput | прямые вызовы движка |
| Поверхность совпадений | окна, хендлы, процессы | любые правки кода/секций |
| Скорость | раунд-трип на чтение, 120+ Гц достижимы батчами | ноль накладных расходов |
| Цена ошибки патча | только смещения | смещения + ABI + перехваты |

Вывод источников однозначен: `src-B` прямо пишет, что база **DETECTED** из-за generic
«trampoline hooking»; `src-C` и `src-F` вообще не подсаживают модули. Поэтому
выбранный нами путь — **внешний доступ, только чтение, без перехватов и без правок кода хоста**.
Запись допускается только в whitelist значений (convar-ы, настройки камеры) и только через
`SendInput`/консоль, не через патч `.text`.

### 2.2 Что именно нельзя трогать

- **Перехваты trampoline/detour** (`funchook` + `distorm`) — публично подтверждённый источник совпадений с шаблоном.
- **Manual mapping**: требует `/Zc:threadSafeInit-` и ломает выгрузку; на Linux встроенный путь
  это `dlopen`. Мы этим не занимаемся.
- **Патч кода хоста** (camera distance «без convar» у `src-C`) — работает, но это
  запись в чужую память и отдельный риск; выносим в опцию, а не в дефолт.

## 3. Дампер смещений = готовый инструмент, свой не пишем

`src-A` (Rust, собран на 1.96.1, форк родственного дампера, MIT) покрывает потребность
полностью:

- Экспорт: `cs`, `hpp`, `json`, `rs`, `zig` + `interfaces.json`, `buttons.json`, `info.json`.
- CLI: `-f` формат, `-i` интервал, `-o` выход, `-p` процесс (`host_bin`), `-c` коннектор, и др.
- Коннекторы memflow: `native` (по умолчанию, без привилегий), `pcileech`, `kvm`, `winio`
  (последние три требуют root/admin).
- Интерфейсный вывод = module-relative адреса фабрик, возвращающих статический объект;
  `dwSoundSystem` верифицирован через `SoundSystem001`, `VMixEditTool001` удалён (не из
  `soundsystem.dll`).
- Недостаток или дублирование сигнатур → дамп останавливается и печатает имя модуля. Это
  штатный сигнал «патч сломал оффсеты», его надо ловить (см. риск R3).
- Запись атомарная: tmp → replace, с откатом при обрыве.
- Живые тесты помечены `--ignored` (нужен запущенный хост); `scripts/check_generated.py
  output --compile-rust --compile-cpp` и CI реально компилируют сгенерированный Rust/C++.

**Ограничение, критичное для Linux-сборки:** сканер читает **PE**. Native-чтение Linux ELF
в этом дампере не реализовано. Значит на Linux смещения либо берутся из готового дампа, либо
дампер гоняется на Windows-машине/в PE-совместимом окружении, либо пишется свой ELF-путь
(отдельная задача, не в M1).

Из дампера мы берём два файла: `offsets.json` (адресные `dw*`) и `client.dll.json` (полевые
`m_*`). Первый у нас уже есть как `contracts/offsets.client-6985.json`; второй — это вывод
того же дампера, который задача T011 нормализует в единственный наш контракт полей:
`contracts/fields.client-<build>.json` (PRINCIPLES P2, P3).

## 4. Методология доказательств (берём из `src-G`)

Главный вывод из RE-артефактов: **одно и то же число может быть доказано четырьмя независимыми
способами, и ни один не имплицирует другой.** В проекте надстроек это прямая шкала надёжности
для любого смещения и любого «знания о семантике поля».

| Класс доказательства | Что это значит | Как выглядит у нас |
|---|---|---|
| identity | адрес/символ опознан по имени из экспорта или из factory-имени | `SoundSystem001` → `dwSoundSystem` |
| byte boundary | доказан только размер/выравнивание, содержимое не доказано | «шаг слота `CGamePlayerSlot` = 24 байта» |
| source path | значение получено из конкретного файла/дампа, воспроизводимо | `offsets.client-6985.json` + SHA-256 |
| semantics | поведение поля подтверждено наблюдением в хосте | «`fog_enable` убирать туман видно глазами» |

Правила, которые переносим как обязательные:

- Каждый опубликованный артефакт сопровождается `MANIFEST.sha256`; приёмка задачи сверяет хэш,
  а не «файл похож».
- Любая запись о смещении помечается уровнем: `established` / `partial` / `contradicted` /
  `not-established`. Запрещено выдавать `partial` за `established`.
- Локальный кэш чужих дампов шифруется (AES-256-GCM в оригинале); у нас достаточно
  read-only кэша + проверки хэша, шифрование — опция (нет смысла усложнять).
- Точки входа в чужой процесс ищутся через `LoadLibraryExW`/`GetProcAddress`-подобный
  символьный поиск, а не жёсткими адресами. У нас это `OffsetRegistry` + сигнатуры.
- Мост «скриптовый слой → native» в оригинале: ~240 обработчиков, лимит FFI на 32 аргумента,
  2 829 путей в меню. Для нас это аргумент в пользу **генерируемых** привязок Lua, а не
  рукописных (см. §11 и T019).

## 5. Семантика смещений build 6985 (то, что реально можно читать)

Три уровня разыменования (см. `contracts/README.md`): **L1** = RVA в модуле, даёт указатель на
объект; **L2** = смещение поля внутри объекта (суффикс `_xxx`); **L3** = статический объект,
разыменовывать не надо (только L1, дальше читаем поля по символам).

| Имя | Модуль | Уровень | Цепочка чтения | Что даёт |
|---|---|---|---|---|
| `dwEntityList` (=`dwGameEntitySystem`) | `client.dll` | L1 | `base_client + off` → указатель на `CGameEntitySystem` | корень списка сущностей |
| `dwGameEntitySystem_entityCount` | `client.dll` | L2 | `entitySystem + 8384` | количество слотов (не максимум индекса) |
| `dwGameRules` | `client.dll` | L1 | `base_client + 104739104` | правила матча, время, команды |
| `dwGlobalVars` | `client.dll` | L1 | `base_client + 97265048` | `tickcount`, `interval_per_tick`, время карты |
| `dwViewRender` | `client.dll` | L1 | `base_client + 104769304` | точка входа для матрицы вида (см. §7) |
| `dwNetworkGameClient` | `engine2.dll` | L1 | `base_engine + 9499792` | клиент сети: локальный оператор, тики, maxClients |
| `dwNetworkGameClient_localPlayer` | `engine2.dll` | L2 | `+248` | первый слот локального оператора |
| `dwNetworkGameClient_maxClients` | `engine2.dll` | L2 | `+576` | число сетевых слотов |
| `dwNetworkGameClient_clientTickCount` | `engine2.dll` | L2 | `+920` | клиентский тик (для интерполяции) |
| `dwNetworkGameClient_deltaTick` | `engine2.dll` | L2 | `+588` | дельта-тик |
| `dwNetworkGameClient_serverTickCount` | `engine2.dll` | L2 | `+588` | **алиас** `deltaTick` — одно и то же число |
| `dwNetworkGameClient_signOnState` | `engine2.dll` | L2 | `+560` | стадия подключения (фильтр «хост идëт») |
| `dwNetworkGameClient_isBackgroundMap` | `engine2.dll` | L2 | `+2888767` | фон-карта → игнорируем лобби/реплей-меню |
| `dwWindowWidth` / `dwWindowHeight` | `engine2.dll` | L2 | `+9518008` / `+9518012` | размер окна → нормализация координат меток |
| `dwInputSystem` | `inputsystem.dll` | L3 | `base_input + 290112` | статический объект ввода (состояние клавиш) |
| `dwSoundSystem` | `soundsystem.dll` | L3 | `base_sound + 6581456` | статический объект звука |

Ключевое ограничение: **полевых `m_*`-смещений в наших артефактах нет** (в дампе не было
`client.dll.json`). Значит список сущностей мы умеем найти, а поля сущности — пока нет.
Это ровно блокер T011; см. §7 и §13.

Правило на все времена: **смещение = данные, а не код.** В `src/` и `include/` запрещено
писать числовые литералы смещений (проверяется `scripts/check_no_hardcoded_offsets.py`);
в коде живут только символические имена из реестра.

## 7. World-to-Screen: где дырка и что именно ждём от T011

В 6985 **нет** `dwViewMatrix` (в `removed_in_6985` числится `dwViewMatrix_static`), поэтому
классическая схема «статическая 4×4 матрица из `engine2.dll`» неприменима.

Рабочая цепочка: `client.dll!dwViewRender` → view-объект → матрица вида + параметры камеры
(FOV,near,far) из его полей. Какие это поля и на каком смещении — **не установлено**
(нет `client.dll.json`). Отсюда жёсткие требования к T011:

- вывод: `contracts/fields.client-<build>.json` (нормализованный `client.dll.json` внешнего
  дампера) со всеми `m_*`, включая группу `m_ViewMatrix`-эквивалент,
  `m_Origin`, `m_Angles`, `m_vecAbsOrigin`, `m_iHealth`, `m_hPlayer`, `m_iTeamNum`,
  `m_lifeState`, `m_bDormant`, `m_fFlags`, `m_ArmorValue`, `m_currentFrame.modelData`,
  `m_spotlightEnd`, цепочки полей воздействий и предметов;
- формат: тот же, что `contracts/offsets.client-6985.json` (плоский JSON, символьные имена);
- проверка: `python scripts/check_contracts.py` + компиляция сгенерированного C++ заголовка;
- блокирующий статус: **без T011 метки, rings, W2S и добивание физически невозможны**; всё
  остальное (реестр, mem-слой, оверлей, конфиг, меню, таймеры на `dwGlobalVars`) — можно
  делать параллельно.

Контракт, который публикуем заранее (чтобы задачи не ждали друг друга):

```cpp
// include/ovr/render/world_to_screen.hpp
namespace ovr::render {
struct View { Mat4x4 matrix; float fov_deg; float aspect; float znear; float zfar;
              Vec3 cam_origin; bool valid; };
bool world_to_screen(const View& view, Vec3 world, Vec2& out_screen);
}
```

Функция чистая и детерминированная → тестируется на фикстурах без хоста (известные
«мир→экран» пары). Это позволяет написать и принять W2S **до** того, как появится живая
матрица: тесты на синтетическом `View`.

## 9. Гигиена профиля: за что реально ограничивают доступ

Из `src-B`: «trampoline hooking = DETECTED» (публично зафиксированный
путь совпадения с шаблоном). Отсюда главное архитектурное решение проекта — **никаких перехватов и правок кода
хоста в M0–M7**. Правила:

- Чтение памяти только из внешнего процесса (`ReadProcessMemory` / `process_vm_readv`),
  никаких записей в `.text`, никаких VMT-подмен, никакой подсадки модулей в default-сборке.
- Manual map **риск совпадения с шаблоном**: в источнике помечен как требующий `/Zc:threadSafeInit-` и
  ломающий выгрузку. Значит если когда-нибудь и переходить на встроенный доступ — только после
  отдельного исследования, не в рамках этих задач.
- Запись в память — только whitelist convar-ов (см. §6), и только через легальный путь
  (консоль/сетевой ввод), а не прямая запись в чужие поля.
- Ввод — `SendInput` / `uinput`, т.е. выглядит как человек с клавиатуры, а не как вызов
  функции хоста.
- Каждый дополнительный артефакт = сигнал: лишнее окно, лишняя строка в списке модулей,
  лишние хэндлы, окно без иконки поверх хоста, необычный тайминг кадра. Отсюда требования к
  оверлею: одно окно, topmost, transparent, без tool-window-мигания, без смены фокуса.
- Рендер оверлея — DX11 или Vulkan (оба подтверждены источниками), не GDI (медленно и
  заметно).
- Путь снижения риска, если обычный внешний доступ начнёт попадать в шаблон: **pcileech/DMA** — тот же
  memflow-коннектор уже есть в дампере, поэтому `IMemoryBackend` проектируется так, чтобы
  pcileech стал просто новым бэкендом без изменения остального кода.

## 10. Windows vs Linux: где что работает

| Аспект | Windows | Linux |
|---|---|---|
| Чтение памяти | `ReadProcessMemory` | `process_vm_readv` |
| Подсадка модуля (если понадобится) | `LoadLibrary` ✅ | `dlopen` ✅ |
| Manual map | ⚠️ риск совпадения, `/Zc:threadSafeInit-` | — |
| Дампер смещений | работает (читает PE) | ⚠️ native ELF-скан не реализован |
| Оверлей | DX11 ✅ / Vulkan ✅ | Vulkan ✅ (+ SDL3 для ввода) |
| Ввод | `SendInput` | `uinput` |
| Зависимости для встроенного режима | `funchook`, `distorm`, Dear ImGui, STB (сигнатуры), DX11/Vulkan, SDL3 | тот же набор |
| Сборка | CMake + MSVC/Clang | `mkdir binlinux && cd binlinux && cmake ../ && make` |

Решение: **Windows-first** (там и дампер, и основная аудитория, и подтверждённые источники),
но весь код пишется так, чтобы Linux появился без переписывания: платформенно-зависимое
только внутри `IMemoryBackend`, `Overlay`-бэкенда и `InputBackend`. Смещения при этом
**разные на двух платформах** → контракт снапшота содержит поля `platform` и `arch`
(наш `info.client-6985.json` = `windows`/`x86_64`).

## 11. Контракт как генерируемый документ + CI (образец `src-H`)

Из `src-H`: API-документация Lua 5.4-скриптов **генерируется**
скриптом `main.py` по списку `urls.txt`, а GitHub Actions по cron **20:00 МСК (17:00 UTC)**
пересобирает генерируемый документ API (`src-H`) и коммитит только при наличии диффа; отдельный workflow
обновляет строку «Last Update». Это готовый шаблон для нас:

- реестр смещений — не «файл, который правят руками», а артефакт, пересобираемый после
  каждого патча хоста;
- человек-читаемый контракт (`contracts/README.md` + сгенерированный список смещений) тоже
  генерируется из JSON, а не ведётся вручную;
- cron-задача: сравнить `ClientVersion` (из `version_file`, т.к. `dwBuildNumber`
  в 6985 удалён) с последней известной → если build изменился, запустить дампер, прогнать
  `check_contracts.py`, поднять PR/задачу «смещения устарели»;
- вывод задач в `TASKS.md` должен быть пригоден для запуска без человека (одна задача =
  один заход), что совпадает с этой моделью CI;
- **провенанс фикстур (PRINCIPLES P8):** один прогон хоста на Windows снимает `RawFrame`-фикстуры
  и JSON-контракты, они коммитятся рядом с `MANIFEST.sha256` (`RESEARCH.md:115`), а Linux-CI
  их только проигрывает; приёмка задачи сверяет хэш, а не «файл похож».

## 12. Что дали Tor и GitHub-поиск (фиксируем как проверенное, чтобы не повторять)

- **Tor** (`.onion`-индексы и форумы локальной карты): по тематике надстроек практически
  ничего. Найденные форумы — это форумы самого Tor Project / Whonix (вопросы про
  маршрутизацию, мосты, `torrc`), а не про Source-приложения и надстройки. Полезный вывод есть: если
  делать **стриминг состояния на вторую машину** (DMA-сценарий), то канал можно гонять через
  Tor и не светить IP; для самих смещений и семантики полей Tor бесполезен.
- **GitHub Search API** в этой сессии отдал пустые ответы (rate-limit анонимных запросов),
  поэтому поиск по коду не является подтверждённым методом; все 9 источников выше получены
  прямым чтением репозиториев/README, а не поиском.
- Итог: вся фактическая база проекта — 9 прочитанных источников + 2 наших снапшота
  смещений. Всё, чего в них нет, помечается как `not-established` и идёт в §13, а не в код.
